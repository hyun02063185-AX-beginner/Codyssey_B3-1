# B3-1 동료 평가 가이드

작성 기준일: **2026-10-24 KST**. 사용자가 전달한 전체 평가항목과 실습 기록을 대응시킨 설명 자료다. 평가기관의 공식 판정이나 전체 통과 선언은 아니다.

## 읽는 방법과 현재 상태

- **실습 확인**: 기존 배포 기록 또는 사용자가 실행해 공유한 결과로 확인했다. 이번 문서 작성 과정에서 AWS 콘솔·SSH·외부 사이트를 새로 점검한 것은 아니다. 현재 상태는 평가 당일 다시 확인한다.
- **설명 답안**: 실제 구성을 근거로 원리와 판단 기준을 설명한다. 답안을 준비했다는 사실이 평가 통과를 뜻하지는 않는다.
- **대응 설계**: 아직 일어나지 않은 장애·확장 상황에 대한 제안이다. DB·ALB·두 번째 EC2를 실제 생성한 것으로 읽지 않는다.
- **미완료**: 리소스 정리를 실행하지 않았고, 최소권한 전용 IAM 역할·정책도 적용하지 않았다. 이 문서를 추가하면서 완료 체크를 하지 않는다.

평가의 외부 접속 검증은 **A: 브라우저 접속**을 선택했다. `GET /health` 방식은 사용하지 않았다. EC2 내부의 `curl -I`는 HEAD 요청에 대한 보조 확인이며, 외부 브라우저 검증이나 `GET /health` 구현을 대신하지 않는다.

```text

```

사용자는 이어서 외부 브라우저의 업데이트 반영을 확인했다. Nginx의 `types_hash` 경고는 있었지만 설정 검증 자체는 성공했다. 이 절은 채팅에 공유한 실행 결과를 옮긴 기록이며, 별도의 원본 터미널 로그·외부 화면 캡처를 새로 생성한 것은 아니다.

## A. 실행 결과 평가항목 전체

<a id="a1"></a>
### A1. VPC, Public Subnet, Internet Gateway, Route Table(0.0.0.0/0 → IGW)이 구성되어 있는가?

**상태: 실습 확인.**

> VPC `10.0.0.0/16` 안에 Subnet `10.0.1.0/24`를 만들고 IGW를 VPC에 연결했습니다. Subnet에 명시적으로 연결한 Route Table에는 VPC 내부의 local 경로와 인터넷 목적지의 `0.0.0.0/0 → IGW` 경로를 구성했습니다. 각 리소스 ID와 연결 관계를 최초 배포 기록과 README에 남겼습니다.

평가 당일에는 IGW 연결 상태, Route Table의 경로 활성 상태와 Subnet 연결을 콘솔에서 다시 확인한다. [아키텍처](architecture.png)는 기존 README에 초안으로 연결되어 있으므로, 파일 존재만으로 최종 도식의 정확성까지 검증됐다고 판단하지 않는다.

<a id="a2"></a>
### A2. EC2에 SSH로 접속 가능하며, 웹 서버가 실행 중인가?

**상태: 실습 확인.**

> SSH 개인키로 Amazon Linux의 `ec2-user` 계정에 접속했습니다. EC2에 Nginx를 설치·활성화했고, 빌드한 `dist`의 내용을 웹 루트에 배치했습니다. Nginx 설정 검사와 서버 내부 HTTP 200, 외부 브라우저 화면까지 확인했습니다.

개인키는 Git에 넣지 않는다. 평가 당일 접속 실패 시 현재 공인 IP와 SSH 규칙, 서버 상태를 먼저 확인한다.

<a id="a3"></a>
### A3. 보안 그룹 인바운드가 “필요 포트만” 허용하며, SSH(22)가 특정 IP로 제한되어 있는가?

**상태: 실습 확인, 현재 규칙 재확인 필요.**

> 인바운드는 공개 웹 서비스용 TCP 80과 관리자 SSH용 TCP 22만 허용했습니다. HTTP는 모든 IPv4 주소에서 접근하게 하고, SSH는 작업 장소의 공인 IP 한 개를 뜻하는 `/32`로 제한했습니다. 사용하지 않는 DB 포트나 HTTPS 443은 열지 않았습니다.

초기 기록의 SSH 소스는 `121.135.181.46/32`다. 이동 시에는 실제 SSH 접속을 실행하는 PC가 사용하는 현재 공인 IP로 갱신한다. 아웃바운드는 기본 전체 허용을 유지했으며, 양방향 규칙 모두 최소화했다고 주장하지 않는다.

<a id="a4"></a>
### A4. 외부 접속이 아래 방식 중 1개로 검증되는가? (제출자가 선택한 방식으로 확인)

- **(A)** 브라우저 `http://<퍼블릭IP>` 접속 시 페이지 정상 로딩
- **(B)** `GET /health` 호출 시 200 및 고정 응답 확인

**상태: A로 실습 확인.**

> A를 선택했습니다. 외부 브라우저에서 `http://13.125.211.95/#/terms`로 접속해 실제 용어사전 화면이 표시되는 것을 확인했습니다. B 방식의 `/health`는 구현하거나 검증하지 않았습니다.

<a id="a5"></a>
### A5. 리소스 정리 체크리스트에서 최소 5종(EC2/EBS/EIP/IGW/VPC) 정리 완료를 확인할 수 있는가?

**상태: 미완료.**

> 현재는 실행 환경을 보존하고 있어서 정리 완료라고 답할 수 없습니다. 정리 순서와 대상 ID는 체크리스트에 준비했습니다. 정리 시 EC2 종료, EBS 삭제 여부, EIP 잔존 여부, IGW 분리·삭제, VPC 삭제를 각각 확인하고 결과를 기록하겠습니다.

EIP는 처음부터 생성하지 않았다. 자동 할당 Public IPv4와 EIP는 구분한다. EIP 항목은 새로 만들었다가 지우는 방식으로 채우지 않고, 미생성·잔존 없음으로 증빙하고 평가자에게 인정 기준을 확인한다. 루트 EBS의 ‘종료 시 삭제: 예’는 설정 확인이며, 실제 삭제 완료가 아니다. Subnet·Route Table·SG 등 의존 리소스도 [체크리스트](cleanup-checklist.md)에 따라 정리해야 한다.

## B. 설명·판단 평가항목 전체

<a id="b1"></a>
### B1. “외부 → IGW → Subnet → EC2”로 이어지는 네트워크 흐름을 다이어그램 기준으로 설명할 수 있는가?

> 방문자가 EC2의 퍼블릭 IP로 HTTP 요청을 보내면 IGW를 통해 VPC의 EC2에 도달할 수 있습니다. IGW는 이 IPv4 구성에서 퍼블릭 IP와 EC2의 사설 IP 사이의 주소 변환도 담당합니다. 해당 Subnet의 네트워크 경로와 EC2 네트워크 인터페이스에 적용된 SG의 허용 조건이 맞으면 Nginx가 요청을 받아 정적 파일을 응답합니다.
>
> VPC와 Subnet은 네트워크 범위이고, Route Table은 경로 규칙입니다. Route Table을 패킷이 통과하는 별도 물리 장비로 해석하지 않습니다. IGW는 인터넷과 양방향 통신을 가능하게 하며, 인바운드 접근 허용 여부는 SG 등에서 제어합니다.

응답은 EC2에서 인터넷 목적지로 보내며 Subnet의 기본 경로가 IGW를 가리킨다. SG는 상태를 추적하므로 허용된 연결의 응답을 허용한다. 모든 네트워크에서 요청과 응답의 물리 경로가 항상 같다는 의미는 아니다. 이 설명은 [IGW 공식 문서](https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Internet_Gateway.html)에 근거한다.

<a id="b2"></a>
### B2. 보안 그룹 규칙을 어떤 기준으로 최소화했는지(허용/미허용 포트) 설명할 수 있는가?

> 실제 사용 목적과 접속 주체를 기준으로 정했습니다. 방문자에게는 웹 포트 80, 관리자에게는 SSH 22만 필요했습니다. SSH는 관리자 접속 장소의 공인 IP로 제한했습니다. DB가 없으므로 DB 포트를 열지 않았고, HTTPS를 구성하지 않았으므로 443도 열지 않았습니다. 기능을 추가할 때 필요한 포트와 출발지를 다시 검토하겠습니다.

현재 SG 인바운드 정책에 대한 설명이다. SSH 키 인증과 SG의 출발지 제한은 함께 사용한다.

<a id="b3"></a>
### B3. 외부 접속 검증을 A 또는 B 중 무엇으로 선택했고, 그 선택을 위해 무엇을 어떻게 구성했는지 설명할 수 있는가?

> 정적 웹페이지의 실제 표시를 보여주기 위해 A를 선택했습니다. 로컬에서 Vite/React/TypeScript 소스를 빌드해 `dist`를 만들고, EC2의 Nginx가 그 파일을 제공하게 했습니다. 퍼블릭 IP, IGW 경로, HTTP 허용 규칙을 구성한 뒤 외부 브라우저에서 화면을 확인했습니다. 서버 내부 점검도 함께 했지만 최종 외부 검증은 브라우저로 했습니다.

브라우저의 `#/terms`는 프런트엔드 HashRouter 경로다. 서버의 `/health` 경로를 만들었다는 뜻은 아니다.

<a id="b4"></a>
### B4. 실습 리소스를 추적/정리하기 위해 어떤 기준(태그, 이름 규칙, 체크리스트)을 사용했는지 설명할 수 있는가?

> 이름을 `b3-1-` 접두사로 통일하고, 계정·리전·리소스 ID와 연결 관계를 기록했습니다. 정리할 때는 이름만 보고 지우지 않고 기록된 ID까지 대조합니다. 체크리스트에는 의존 관계에 따른 정리 순서와 확인 결과를 남기도록 했습니다. 기본 VPC, 다른 실습, 조직 관리 계정은 보호 대상으로 구분했습니다.

`Mission=B3-1` 추가 태그는 일괄 적용 여부가 증빙되지 않았으므로 적용 완료로 말하지 않는다. Name 이름 규칙과 실제 리소스 ID 기록을 근거로 설명한다.

<a id="b5"></a>
### B5. Public Subnet Route Table의 기본 경로(0.0.0.0/0 → IGW)가 필요한 이유를 설명할 수 있는가?

> VPC 내부 주소는 local 경로로 통신합니다. 인터넷의 다른 주소로 보내는 트래픽에는 목적지로 가는 경로가 더 필요해서, 다른 구체적인 경로에 해당하지 않는 IPv4 목적지를 IGW로 보내도록 기본 경로를 지정했습니다. IGW를 VPC에 붙여 놓기만 해서는 이 Subnet이 인터넷 경로를 사용하지 않습니다. 웹 요청에 대한 인터넷 방향 응답에도 이 경로가 필요합니다.

Public Subnet은 IGW로 직접 가는 경로가 있는 Subnet이다. 그 안의 모든 서버가 자동으로 공개되지는 않는다. 이 구성의 EC2에는 Public IPv4, SG·NACL 허용, Nginx 실행도 필요하다.

<a id="b6"></a>
### B6. Security Group과 IAM의 책임 범위 차이를 설명하고, “최소 권한”이 왜 필요한지 설명할 수 있는가?

> SG는 EC2 네트워크 인터페이스를 오가는 통신을 출발지·프로토콜·포트 기준으로 제어합니다. IAM은 AWS에서 누가 어떤 리소스에 어떤 작업을 할 수 있는지 관리합니다. 웹 80번 접속을 허용하는 것과 EC2를 생성·삭제할 권한을 주는 것은 서로 다른 문제입니다.
>
> 필요한 범위만 허용하면 실수나 자격 증명 유출 때 영향을 줄일 수 있습니다. 이번에는 SSH 출발지를 제한했고 서버에 불필요한 AWS 역할을 붙이지 않았습니다. 다만 관리 작업 역할에는 AdministratorAccess가 연결되어 있어서 IAM 최소권한 적용을 완료했다고 말할 수는 없습니다.

SSH 개인키는 Linux 접속 인증 수단이며, IAM 관리 작업 권한과 구분한다. 관리 역할의 권한 축소 작업은 미실행 상태다.

<a id="b7"></a>
### B7. SSH(22) 또는 DB 포트를 0.0.0.0/0로 열면 안 되는 이유와 대안을 설명할 수 있는가?

**실제 적용: SSH `/32` 제한. DB 관련 내용은 대응 설계.**

> `0.0.0.0/0`는 모든 IPv4 주소에서 접속을 시도할 수 있다는 뜻입니다. SSH는 서버 관리 통로이고 DB는 데이터를 다루는 통로라서 전체 공개하면 자동 스캔과 로그인 공격에 노출되는 범위가 커집니다. 개인키나 비밀번호 인증이 있어도 출발지를 함께 제한하겠습니다.
>
> 이번에는 HTTP 80만 전체 공개하고 SSH 22는 작업 장소의 공인 IP 한 개를 뜻하는 `/32`로 제한했습니다. 다른 장소로 이동하면 새 공인 IP를 확인해 규칙을 바꾸겠습니다. DB를 추가한다면 인터넷 전체에 공개하지 않고 필요한 애플리케이션 서버의 SG에서만 접근하도록 구성하겠습니다.

필요에 따라 VPN이나 적절한 IAM·에이전트·통신 경로를 구성한 SSM Session Manager도 관리자 접속 대안이 될 수 있다. 현재는 이 대안들을 설정하지 않았다. 공용 PC의 공인 IP를 여러 사람이 공유한다면 `/32`만으로 접속자를 식별할 수 없으므로 SSH 키 인증도 계속 필요하다.

참고: [용도별 SG 규칙](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/security-group-rules-reference.html).

<a id="b8"></a>
### B8. 트러블슈팅에서 “가설 → 검증” 순서를 유지한 이유와, 로그/근거를 어떻게 활용했는지 설명할 수 있는가?

**실제 사례: 서울 리전 VPC 생성의 SCP explicit deny.**

> 여러 설정을 한꺼번에 바꾸면 무엇 때문에 해결됐는지 알기 어렵고, 불필요하게 권한이나 포트를 열 수도 있습니다. 그래서 관찰한 오류로 원인을 예상하고, 그 예상과 관련된 설정을 확인한 뒤 필요한 부분만 변경했습니다.
>
> 서울에서 VPC 생성이 거부됐을 때 오류 메시지의 SCP explicit deny를 단서로 조직 리전 제한을 확인했습니다. 허용 리전에 서울이 빠져 있었고 서울만 추가한 뒤, Building Things에서 같은 작업을 다시 실행해 생성 성공을 확인했습니다. 이 과정이 가설, 확인, 변경, 재검증의 사례입니다.

| 단계 | 실제 사례에서 설명할 내용 |
|---|---|
| 관찰 | `ec2:CreateVpc` 요청이 SCP explicit deny로 실패 |
| 가설 | 조직의 허용 리전 목록이 서울을 제외했을 가능성 |
| 검증 | `RegionFloor`의 `aws:RequestedRegion` 목록에 서울이 없는지 확인 |
| 조치 | `ap-northeast-2`만 추가 |
| 재검증 | Building Things·서울에서 `b3-1-vpc` 생성 성공 |

오류 메시지, 정책 JSON, 명령 결과, 설정 전후 값도 근거다. CloudTrail이나 Nginx 로그는 상황에 따라 추가로 확인할 수 있지만 이 SCP 사례에서 실제로 열어 보았다고 주장하지 않는다. 기존 근거는 [문제 해결 기록 A](troubleshooting.md#a-서울-리전-vpc-생성이-scp-explicit-deny로-거부됨)다. 원본 콘솔 오류 캡처를 이 문서에서 새로 확보한 것은 아니다.

<a id="b9"></a>
### B9. 외부 접속이 안 될 때, 어떤 순서로(라우팅 → SG → 퍼블릭 IP/DNS → 서버 프로세스/로그) 점검하는지 설명할 수 있는가?

**대응 절차.**

> 먼저 올바른 계정·서울 리전인지와 EC2 실행 상태를 확인하겠습니다. 이어서 인터넷 경로, 접근 허용 규칙, 접속 주소, 서버 내부 상태를 차례로 확인해 문제가 생긴 범위를 좁히겠습니다. 확인한 결과를 기록하면서 한 번에 필요한 설정만 바꾸겠습니다.

| 순서 | 확인 내용 | 판단에 사용할 근거 |
|---|---|---|
| 1. 라우팅 | 해당 VPC의 IGW 연결, 해당 Subnet의 Route Table 연결, `0.0.0.0/0 → IGW` 활성 상태 | 연결된 ID와 경로 상태 |
| 2. SG | EC2에 붙은 SG의 TCP 80 허용. SSH 문제라면 TCP 22의 현재 작업자 공인 IP `/32` | 실제 인바운드 규칙과 접속 출발지 |
| 3. Public IP/DNS | EC2의 현재 Public IPv4, 브라우저의 `http://` 주소. 도메인 사용 시 DNS 해석도 확인 | EC2 현재 주소와 접속한 주소 비교 |
| 4. 서버 프로세스·로그 | Nginx 실행·80번 listen·설정·배포 파일·권한·정적 자산 요청 | 서비스 상태, 내부 curl, 접근·오류 로그 |

SSH에 접속할 수 있을 때의 서버 내부 확인 예시는 다음과 같다.

```sh
sudo systemctl status nginx --no-pager
sudo nginx -t
sudo ss -lntp
curl -I http://localhost
sudo tail -n 50 /var/log/nginx/access.log
sudo tail -n 50 /var/log/nginx/error.log
```

이 명령들은 점검 예시이며 이번 문서 작성 중 새로 실행하지 않았다. 내부 HTTP 200은 외부 경로와 브라우저의 JS 실행까지 증명하지 않으므로 외부 화면·자산 로딩도 확인한다. 위 단계에서 원인이 안 나오면 기본 NACL 변경 여부와 OS 방화벽 등도 점검한다.

이 순서는 진단 순서다. 패킷이 각 AWS 서비스를 물리 장비처럼 차례로 통과한다는 의미가 아니다. 기존 troubleshooting 문서처럼 현재 IP를 먼저 확인하는 것도 가능하며, SSH 시간 초과와 `Permission denied (publickey)`처럼 증상에 따라 우선순위를 조정한다.

<a id="b10"></a>
### B10. IAM 권한이 부족해 작업이 실패했다면, “권한을 무작정 올리지 않고” 어떤 방식으로 필요한 최소 범위를 찾아갈지 설명할 수 있는가?

**실제 SCP 사례 + 향후 대응 절차. 최소권한 전용 역할 적용은 미완료.**

> 먼저 현재 계정과 역할을 확인하고, 오류에서 거부된 작업, 대상 리소스, 리전과 조건을 찾겠습니다. 허용 권한이 빠진 것인지, SCP나 다른 정책의 명시적 거부인지 구분하겠습니다.
>
> 허용이 부족하다면 서비스가 지원하는 범위에서 필요한 작업과 리소스·조건만 추가하겠습니다. 명시적 거부라면 관리자 권한을 더 붙이기보다 제한 목적과 미션에 필요한 예외 범위를 확인하겠습니다. 변경 후 원래 실패한 작업을 재실행하고 관련 없는 권한까지 열리지 않았는지도 확인하겠습니다.
>
> 이번 서울 문제는 역할에 관리자 권한이 있어도 SCP에 막힐 수 있다는 사례입니다. 조직 정책의 서울 허용 여부를 확인해 필요한 범위만 수정했습니다.

현재 신원 확인에는 `aws sts get-caller-identity`를 사용했다. 오류 진단에서는 역할의 연결 정책·인라인 정책, Permissions Boundary, SCP 등 적용 정책을 확인한다. 리소스별 제한을 지원하지 않는 조회 작업 등은 `Resource: "*"`가 필요할 수 있으므로, 모든 작업이 특정 ARN 하나로 제한된다고 가정하지 않는다. 지원되는 경우 리전·태그 등 조건도 검토한다.

참고: [Access denied 진단](https://docs.aws.amazon.com/IAM/latest/UserGuide/troubleshoot_access-denied.html). 조직 정책 변경은 해당 정책을 관리할 권한과 운영상 승인 범위 안에서 수행한다.

<a id="b11"></a>
### B11. 트래픽이 늘어 “인스턴스를 2대로 늘려야” 한다면, 현재 구조에서 무엇이 병목이며 어떤 구성요소(ALB 등)를 추가할지 설명할 수 있는가?

**대응 설계. ALB·두 번째 EC2·추가 Subnet은 미구축.**

> 현재는 EC2 한 대가 모든 요청을 처리하므로 처리 용량에 한계가 있고 그 서버가 멈추면 서비스도 중단됩니다. 다만 실제 병목이 CPU인지 네트워크인지 측정한 것은 아니므로 CPU 사용률, 응답 시간, 오류율과 네트워크 지표 등을 먼저 확인하겠습니다.
>
> 두 대로 확장한다면 두 EC2에 같은 빌드 결과물을 배포하고, 앞에 ALB를 두겠습니다. 방문자는 ALB의 DNS 이름이나 연결한 도메인으로 접속하고, ALB가 정상인 서버에 요청을 분산하도록 하겠습니다. EC2를 한 대 더 만들기만 하면 기존 IP의 요청이 자동 분산되지는 않습니다.
>
> 가용성도 높이려면 서로 다른 가용 영역에 배치하겠습니다. 현재 Subnet은 하나이므로 다른 가용 영역에 Subnet을 추가하겠습니다. EC2의 웹 포트는 ALB의 SG에서 오는 요청만 허용하도록 바꾸겠습니다.

| 추가·변경 구성 | 역할 |
|---|---|
| 다른 가용 영역의 Subnet과 두 번째 EC2 | 처리 용량 분산 및 가용 영역 장애 대비 |
| 인터넷 공개 ALB와 Listener | 공통 접속 지점에서 HTTP 요청 수신 |
| Target Group | 두 EC2를 요청 전달 대상으로 등록 |
| Health Check | 예: 정적 사이트의 `/` 응답이 200인지 검사하고 정상 대상으로 요청 전달 |
| SG | ALB는 공개 웹 요청 허용, EC2 웹 포트는 ALB SG에서만 허용. SSH는 관리 출발지로 별도 제한 |
| 배포 절차 | 두 서버에 동일 버전 배포·검증, 필요 시 나중에 Auto Scaling 검토 |

일반적인 ALB 가용 영역 구성은 서로 다른 두 가용 영역의 Subnet이 필요하다. 웹 파일만 제공하는 현재 사이트에는 DB가 없으므로 DB 병목이 있다고 설명하지 않는다. ALB는 용량과 가용성 개선을 위한 제안이며 실제 비용이 추가되므로 이번 답안을 위해 생성하지 않는다.

참고: [Application Load Balancer와 Subnet](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html).

<a id="b12"></a>
### B12. Billing에 예상치 못한 비용이 찍혔다면, 어떤 리소스부터 의심하고 어떻게 추적/정리할지 설명할 수 있는가?

**대응 절차. 특정 비용의 리소스별 원인은 아직 확정하지 않음.**

> 먼저 Billing의 Bills나 Cost Explorer에서 어느 계정·리전·서비스·사용 유형에서 비용이 발생했는지 확인하겠습니다. 크레딧 사용액과 실제 결제 금액도 구분하겠습니다. 조직으로 계정이 나뉘어 있으므로 비용이 발생한 연결 계정까지 확인하겠습니다.
>
> 우리 구성에서는 방문자가 없어도 발생할 수 있는 EC2 실행 시간, 퍼블릭 IPv4, EBS 비용을 먼저 확인하겠습니다. 그다음 데이터 전송이나 사용하지 않는 볼륨·스냅샷·EIP, 다른 리전의 리소스가 있는지 확인하겠습니다. NAT Gateway나 ALB는 현재 만들지 않았으므로 실제 청구 내역에 나타나는지 확인하고 판단하겠습니다.
>
> 비용 항목과 리소스 ID를 대조하고 불필요한 리소스만 정리하겠습니다. EC2는 Stop만 해도 EBS 비용이 남을 수 있습니다. 우리 루트 EBS는 종료 시 삭제 설정이지만, 실제 종료 후에도 삭제 여부를 확인하겠습니다. 반영 지연을 고려해 나중에 비용 화면도 다시 확인하겠습니다.

| 추적 단계 | 확인할 내용 |
|---|---|
| Billing → Bills / Cost Explorer | 대상 월, 연결 계정, 리전, 서비스, 사용 유형, 크레딧·청구 구분 |
| EC2 | 실행 중 인스턴스와 실행 기간, 필요 시 T3 Unlimited의 추가 CPU 크레딧 사용 유형 |
| VPC·EC2 주소 | Public IPv4 사용과 EIP 잔존 여부 |
| EBS·Snapshot | 실행 중·분리된 볼륨, 스냅샷의 잔존과 용량 |
| 기타 서비스·다른 리전 | 청구에 나타난 서비스를 따라 실습 외 생성 여부 확인 |
| 정리·후속 확인 | 실습 ID 대조, 체크리스트 실행, 반영 지연 후 재확인 |

현재 서버 보존 방침을 이 답안 때문에 변경하지 않는다. 정리는 사용자가 정리 시점을 결정한 뒤 수행한다. 예산 알림은 자동 지출 상한선이 아니며, 알림 조건과 수신 여부도 별도로 확인해야 한다. 특정 알림 금액·수신 성공을 증빙 없이 완료로 기록하지 않는다.

참고: [예상하지 못한 비용 점검](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/checklistforunwantedcharges.html), [Budgets 모범 사례](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-best-practices.html), [T 계열 Unlimited](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-performance-instances-unlimited-mode.html).

## 평가 전 확인·후속 기록

- [ ] 평가 당일 현재 계정·리전·IP·SG 규칙·SSH·외부 화면 확인
- [ ] 필요한 실제 캡처·실행 결과를 evidence 안내에 따라 민감 정보 가림 후 보관
- [ ] 기존 아키텍처 초안의 실제 구성 일치 여부와 최종 표현 확인
- [ ] IAM 최소권한의 설명과 실제 적용 상태를 구분해 평가자에게 전달
- [ ] 미실행 정리 항목과 EIP 미생성 항목의 평가 처리 기준 확인
- [ ] 정리 시점이 결정되면 cleanup 체크리스트 실행 및 결과 기록

이 문서에서는 위 항목의 실행 완료를 새로 선언하지 않는다. 사용자 제공 평가항목은 A 5개와 B 12개, 총 17개이며 선택지 A/B는 A4에 함께 보존했다.
